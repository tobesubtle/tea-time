# Next.js Framework 가이드라인

이 프로젝트에서 Next.js (App Router)를 사용할 때 지켜야 할 핵심 원칙과 권장 사항입니다.

## 1. 컴포넌트 렌더링 (Server vs Client)
* **Server Component 우선 사용 (Default):** 모든 컴포넌트는 기본적으로 서버 컴포넌트로 작성합니다. 데이터 페칭과 백엔드 리소스 접근은 서버 컴포넌트에서 처리하여 클라이언트 번들 사이즈를 줄이고 성능을 최적화합니다.
* **Client Component 최소화:** 상태 관리(`useState`, `useReducer`), 생명주기 이벤트(`useEffect`), 브라우저 전용 API(DOM, `window`) 또는 상호작용(onClick 등)이 반드시 필요한 경우에만 파일 최상단에 `"use client"`를 선언하여 사용합니다.
* **말단(Leaf) 노드에 Client Component 배치:** 클라이언트 컴포넌트는 컴포넌트 트리의 최대한 말단에 배치합니다. 클라이언트 컴포넌트 안에서 서버 컴포넌트를 직접 import 하는 것을 피하고, 필요하다면 `children` prop으로 넘겨받는 패턴을 사용합니다.

## 2. 코드 가독성 및 모듈화
* **명확하고 간결한 코드 작성:** 함수와 변수명은 그 역할을 명확히 드러내도록 작성합니다. 코드를 읽는 사람이 흐름을 쉽게 파악할 수 있도록 복잡한 중첩이나 조건문은 피하고, 간결성을 유지합니다.
* **파일 분할 (관심사 분리):** 하나의 파일(예: `page.tsx` 또는 컴포넌트)의 코드 라인이 너무 길어지거나 여러 가지 역할이 섞이게 되면, 작은 단위의 UI 컴포넌트, 커스텀 훅(`hooks/`), 유틸리티 함수(`utils/`) 등으로 파일을 적절히 분할합니다.

## 3. 데이터 페칭 및 상태 변경 (App Router 특화)
* **`useEffect`를 활용한 페칭 지양:** 특별한 이유가 없다면 클라이언트 사이드에서 `useEffect`를 사용한 데이터 페칭을 지양하고, **서버 컴포넌트 내에서 `async/await`를 사용한 직접 페칭**을 권장합니다.
* **Server Actions 활용:** 데이터 생성, 수정, 삭제(Mutation)나 폼(Form) 제출은 별도의 API Route(`/app/api/...`)를 만들기보다는 **Server Actions**(`"use server"`)를 우선적으로 활용하여 구현합니다.

## 4. Next.js 내장 최적화 기능 적극 활용
* **예약어 파일 컨벤션 준수:** `page.tsx`, `layout.tsx` 외에도 로딩 상태는 `loading.tsx`, 에러 처리는 `error.tsx`, 데이터 페칭 전 스켈레톤 UI 등 Next.js의 선언적 라우팅 시스템을 적극 활용합니다.
* **내장 컴포넌트 사용:** 이미지는 렌더링 최적화를 위해 반드시 `next/image`의 `<Image />` 컴포넌트를 사용하고, 페이지 간 이동은 `next/link`의 `<Link />`, 폰트는 `next/font`를 사용하여 성능을 극대화합니다.
